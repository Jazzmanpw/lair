# Reminder And Inquiry Shared Prototype Guidance

## Purpose

This reference carries only the common constraints needed by agents or humans working on reminder and inquiry prototype tasks. The [prototype index](./tasks/reminder-inquiry-item-prototypes.md) owns orchestration order. The [candidate inventory](./shared-surface-candidate-inventory.md) owns evidence and routing decisions. Individual task files own local alternatives and examples.

## Shared Guidance

- A reminder represents a consequence that should occur when its condition is met and could be missed if the GM forgets it.
- An inquiry reference offers intentionally authored roll-guarded discovery material the GM can consult when players seek information.
- Candidate source type does not determine item grammar. One source may contribute several runtime items with distinct grammar.
- T1 may be explicitly authored. Do not require prototypes to derive compact lines from source prose.
- T2 reveals locally authored resolution content and explicit references. Do not add automatic rules adjudication, DC calculation, or cross-note composition.
- Any item may include explicit references to other notes or system material. Detailed contextual retrieval behavior belongs to a separate cross-mode prototype.
- Exploration and tactics may change priority, wording, or compact metadata without automatically removing candidate families.

## Shared Prototype Contract

Each item study should:

- use representative Russian Salty Scars content and at least one difficult sample;
- compare materially different internal treatments rather than cosmetic themes;
- show T1 at realistic list width even before the list is designed;
- test the item's plausible T2 resolution content and interactions;
- identify explicit reference targets without implementing the future reference browser;
- distinguish stable input, prototype hypothesis, and questions requiring later list context;
- record provisional Building Mode implications, especially whether T1 needs explicit authoring;
- use fixture-only view models while the domain shape remains unsettled.

Item studies must not settle final grouping, surface count, list dimensions, filtering, ordering, keyboard behavior, or full-layout placement.

## Lightweight Scan Quiz

Each item study should include a lightweight scan test before its results are treated as ready for list composition:

- build a representative set of rows, including long authored text and at least one difficult neighboring item;
- present player-declaration or fiction-state prompts such as "I inspect the runes above the chair" or "a creature is hit with a spear";
- have the developer find the relevant item and note what caught attention, what misled, and whether the item felt like a suggestion rather than prepared context;
- preserve the prompts, observations, and method problems in the prototype's follow-up design-memory artifact so the scan quiz itself can improve over later tasks.

## Shared Questions

- How short and discriminating can each T1 line remain at realistic widths?
- Which metadata supports recognition without turning type taxonomy into the main content?
- Which T2 treatments preserve orientation and allow comparison with nearby items?
- Which item states are content, runtime annotation, availability, dismissal, or temporary UI focus?
- Do reminder and inquiry items need wider scan lanes than scene details, even when they eventually use separate surfaces?
- Where can reminder and inquiry items reuse visual language without implying equal urgency?
- What evidence would justify one combined surface, neighboring surfaces, or a later split?
